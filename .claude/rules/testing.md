# Testing Requirements

## 1) 每個變更都帶測試

- 新功能有對應的測試；改了行為就改或加測試；修 bug 先寫一個會失敗的測試，再修。
- 每個行為至少涵蓋：正常路徑、無效輸入、邊界（空、零、上限）、失敗路徑（依賴出錯、逾時）。
- 票的驗收條件，每一條都要對得到一個實際跑過的測試；審查會拿測試名稱與測試輸出來核對。

## 2) 測試品質三道 gate

每個測試新增前過三關，審視既有測試時也照此評：

1. **可觀察行為**：斷言打得到的介面（回傳值、回應、ViewModel 的狀態、設定表），不 probe 內部狀態、私有欄位或背景工作的協調狀態；要驗內部狀態就在該層寫單元測試，不要偽裝成 e2e。
2. **真實情境**：流程對應實際的使用方式。純 regression guard 可以有，但名稱或註解必須標明防的是哪個 bug。若測試只有靠違反正式環境的不變量（如重置一次性的狀態）才能通過，錯的是測試。
3. **assertion 強度**：驗業務語意，不是 `err == nil`、`len(x) > 0`、`NotNull`。名字說「冪等」就驗第二次呼叫沒有效果；說「擋下」就驗真的被擋；說「保留」就顯式比對前後的狀態。

## Workflow

- **Bug 修復、小功能**：優先 TDD（先寫失敗的測試 → 實作 → 轉綠）。
- **新模組、大功能**：可以先實作，但同一個 PR 內補齊每個對外操作與關鍵 usecase 的測試。
- 測試失敗時先查隔離與 fake 對不對；**修實作，不是修測試**（除非測試本身錯了，那就改測試，並在 PR 裡說明）。
- 不跳過、不註解掉失敗的測試來交差。
